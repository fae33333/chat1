# ★ كشف النكات + التحديث اللحظي — ملاحظات التعديل

## ملخص سريع

| المطلوب | الحالة | ملاحظة |
|---|---|---|
| عدّاد الغرفة `1/500 → 2/500` لحظياً | ✅ كان يعمل أصلاً + تم تقويته | `emitRoomCounts()` عند كل دخول/خروج |
| الحظر يُخرج الشخص فوراً ويخفي اسمه | ✅ تم إصلاح ثغرتين | مسح شامل لكل الغرف + تنظيف `onlineUsers` |
| الطرد والكتم لحظياً | ✅ كان يعمل، وتم التحقق باختبار | يصمد بعد «تحديث الدردشة» |
| زر **كشف نكات** للإدارة | ✅ جديد | ادمن / سوبر ادمن / سوبر ماستر فقط |
| عرض الأسماء من نفس الـ IP + الوقت + IP + الدولة | ✅ جديد | جدول `login_history` + خدمة تحديد الدولة |

---

## 1) العدّاد اللحظي وقوائم المستخدمين

كان النظام يبثّ `roomCounts` و`roomUsers` أصلاً عند كل دخول ومغادرة، وأثبت الاختبار أن
العدّاد يرتفع من `1` إلى `2` فوراً دون تحديث الصفحة. لم يكن هناك خلل هنا.

## 2) إصلاح الحظر (خلل حقيقي تم اكتشافه)

**المشكلة الأولى — اسم يبقى معلّقاً في الغرفة:**
كان الحظر يجمع الغرف المتأثرة من الجلسات الحيّة (`socket.data.joinedRooms`) فقط. فإذا كان
المحظور ضمن «مهلة إعادة الاتصال» (8 ثوانٍ بعد انقطاع الشبكة) يبقى اسمه في `roomUsers`
دون أي سوكيت حيّ، فلا يُحذف ويستمر ظاهراً في القائمة والعدّاد.

الحل: مسح شامل لكل الغرف التي يظهر فيها اسمه:
```js
for (const roomId of Object.keys(roomUsers)) {
  for (const removedUid of removedUserIds) {
    if (!roomUsers[roomId] || !roomUsers[roomId].has(removedUid)) continue;
    affectedRoomIds.add(+roomId);
  }
}
...
for (const removedUid of removedUserIds) delete onlineUsers[removedUid];
```

**المشكلة الثانية — حضور وهمي بعد اتصال مرفوض:**
عند `connection` كان الخادم يسجّل المستخدم في `onlineUsers` و`userSockets` **قبل** فحص
الحظر وتعارض الجلسة. وعند الرفض كان ينفّذ `return` قبل تسجيل مستمع `disconnect`، فيبقى
أثر وهمي في قوائم الحضور. أُضيفت `abortConnection()` لتنظيف الأثر في مساري الخروج المبكر.

## 3) كشف النكات

### قاعدة البيانات — `login_history`
جدول جديد يسجّل كل دخول ناجح: `user_id, username, ip, device_id, country, country_code,
registered, created_at`. يُقصّ تلقائياً إلى آخر **50** دخول لكل حساب حتى لا ينمو بلا حدود.

### تحديد الدولة
`lookupIpCountry(ip)` عبر `ip-api.com` مع:
- ذاكرة مؤقتة 12 ساعة لكل IP (لا استدعاء خارجي عند كل دخول)
- مهلة 3.5 ثانية + `AbortController`
- أسماء الدول بالعربية (`COUNTRY_AR`)
- العناوين المحلية تُعرض «شبكة محلية»، والفشل يعطي «غير معروف» — **لا يعطّل الدخول أبداً**
- يمكن تعطيلها بالكامل عبر `IP_GEO_DISABLED=1`

التسجيل يجري بصيغة «أطلق وانسَ» داخل `finishAuthentication` فلا يضيف أي تأخير على الدخول.

### الواجهة البرمجية
`GET /api/admin/users/:id/aliases`

يجمع الأسماء من مصدرين (سجل الدخول + جدول المستخدمين) مطابقةً على **الـ IP أو معرّف الجهاز**،
ويعيد لكل اسم: `username, ip, country, last_login, logins, online, registered, rooms`.

يفضّل عنوان الـ IP من الجلسة الحيّة إن وُجدت، وإلا آخر قيمة محفوظة.

### الصلاحية (طبقتان)
- **الواجهة:** الزر يظهر عبر `us-staff-only` للإدارة العامة فقط، ويختفي عند النقر على النفس.
- **الخادم:** يعيد التحقق من `req.authRank` ويرفض بـ 403 — **أدمن الغرفة لا يرى عناوين IP**.

### إصلاح جانبي في `requireModerator`
كان يقرأ `req.body.room_id` مباشرة، وطلبات GET في Express 5 بلا جسم مُحلَّل → ‏`TypeError`‏ و500.
أصبحت القراءة آمنة من `body`/`query`/`params`.

# 👑 بانر الدخول الملكي فوق كل شيء

## المطلوب
`rt-banner-tiktok` (صورة + اسم + «دخول ملكي») يظهر **فوق كل شيء**، وباقي المشهد
(الخلفية والصورة المتحركة) يبقى **بالخلفية كما هو**.

## السبب الجذري
1. العنصر `#royalEntryLayer` يحمل دائماً الكلاس `behind-chat` في `index.html`،
   والجافاسكربت **لا يزيله أبداً**.
2. `.behind-chat` تضع `opacity: 0.2` على الطبقة بأكملها.
3. `.royal-fs` ترفع `z-index` إلى 99999 لكنها **لا تُعيد** `opacity` إلى 1
   (بعكس مشهد الهدية الذي يعيدها صراحةً في `.rt-gift-king-stage`).

**النتيجة:** البانر يُرسم بشفافية 20% فقط. والأهم أن أي `opacity < 1` تُنشئ
**سياق تكديس (stacking context)** يحبس `z-index` الخاص بالبانر داخل الطبقة الباهتة،
فلا يستطيع الظهور فوق الدردشة **مهما رفعنا قيمة z-index**.

## الحل
لا يمكن إخراج عنصر للأعلى وهو داخل أب شفاف — لذلك نُقل البانر إلى **طبقة مستقلة**:

- `<div id="royalBannerLayer">` جديدة في `index.html` بشفافية كاملة و`z-index:1000000`
- `showRoyalBanner()` / `hideRoyalBanner()` لعرضه وتنظيفه
- `pointer-events:none` تبقى — البانر لا يحجب النقر على الدردشة
- مشهد الدخول (الخلفية + الصورة) **لم يُمَس** ويبقى خلف الدردشة تماماً كما هو
- طُبِّق على **بانر الدخول الملكي وبانر الهدية الملكية** معاً
- كل مشهد جديد يلغي مؤقّتات المشهد السابق حتى لا يُخفي بانر الجديد

## الاختبار — `test-royal-banner.js`

# 🎁 هدايا حساب عبر الإدارة (بحث + عرض + حذف)

## المطلوب
البحث عن حساب من لوحة الإدارة، وعرض الهدايا الخاصة به، وإمكانية حذفها.

## الواجهة
صفحة جديدة: **الهدايا والإيموجي ← هدايا حساب (بحث وحذف)** — للسوبر ادمن والمالك فقط.

1. حقل بحث بالاسم (نفس نمط صفحة «تحرير مستخدم»)
2. زر **عرض الهدايا** بجانب كل حساب
3. بطاقات إحصائية: عدد السطور • إجمالي القطع • **مجموع الذهب**
4. قائمة الهدايا: الصورة/الإيموجي، الاسم، الكمية، **المرسِل**، قيمة الذهب، وتاريخ الاستلام
5. **حذف** لكل هدية + **حذف كل الهدايا** دفعة واحدة — مع تأكيد قبل التنفيذ
6. الإجماليات تتحدث فورياً بعد كل حذف دون إعادة تحميل الصفحة

## الواجهة البرمجية
| المسار | الوظيفة |
|---|---|
| `GET /api/admin/users/:id/gifts` | هدايا الحساب + الإجماليات + حالة التسكير |
| `DELETE /api/admin/users/:id/gifts/:giftId` | حذف هدية واحدة |
| `DELETE /api/admin/users/:id/gifts` | حذف كل هدايا الحساب |

## اعتبارات مهمة
- **حماية من تخطي الملكية:** الحذف مقيّد بـ `WHERE id=? AND to_id=?` — تمرير معرّف
  هدية تخص حساباً آخر يُرفض بـ 404 ولا تتأثر بيانات الغير (مختبَر).
- **حماية الرتب:** لا يستطيع السوبر ادمن عرض/حذف هدايا حساب المالك (`supermaster`).
- **تنبيه التسكير:** إذا كان للحساب طلب تسكير قيد المراجعة يظهر تحذير واضح، لأن الحذف
  يُنقص ما سيُخصم عند اتمام الطلب.
- **الذهب لا يُعاد:** الحذف يزيل سجل الهدية فقط ولا يسحب/يعيد ذهباً من رصيد الحساب،
  وهذا موضّح للمشرف في الصفحة وفي رسالة التأكيد.
